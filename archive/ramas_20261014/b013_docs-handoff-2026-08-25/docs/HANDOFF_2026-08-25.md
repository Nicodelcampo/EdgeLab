## 1. Qué es esto, en dos párrafos

Hay un indicador de trading llamado **BigTrap2Absorption**. Existe dos veces: una en
NinjaTrader (C#) y otra en Python. La versión Python es la que se usa para investigar.

Antes de medir si el indicador **sirve para ganar plata**, hay que probar dos cosas: que
las dos versiones **calculan exactamente lo mismo**, y que se entiende **qué hace cada una
de sus 21 perillas**. Las dos cosas están casi terminadas. **Lo de ganar plata no se midió
nunca, a propósito.**

---

## 2. Lo que se hizo, en orden

### 2.1 Se probó que las dos versiones coinciden

Se comparó la versión C# contra la Python sobre datos reales de oro. Coinciden. Quedó
firmado como `FINAL_PUERTA0_SIGNED`.

**Pero se probó sólo con los valores por defecto de las 21 perillas.**

### 2.2 Se movieron las perillas y apareció un defecto

Se corrieron 51 configuraciones moviendo **una perilla por vez**. Resultado: las perillas
se dividen en tres grupos.

| grupo | qué hace | cuántas |
|---|---|:-:|
| **cambian cuántas señales aparecen** | lo esperable | 15 |
| **cambian cuánto vive cada señal** | invisible si sólo contás señales | 3 |
| **no hacen nada** | decorativas | 3 |

El grupo del medio fue el hallazgo: `MaxAgeBars`, `MaxTouches` e `InvalidationMode` dan
**exactamente la misma cantidad** de señales con cualquier valor. Parecen decorativas. No
lo son: una de ellas hace que las señales vivan tanto que los toques pasan de 9.400 a
**223.000**.

### 2.3 Y apareció un defecto real de paridad

**`MinExportVolume`**: la versión C# la usa para filtrar; la Python la leía y **la tiraba**.

Nadie lo vio en seis rondas de auditoría porque el valor por defecto es `1.0`, y con ese
valor el filtro **nunca se activa**. Las dos versiones coincidían por casualidad.

**Ya está arreglado** (`ee07c34`), con el mismo orden de evaluación que el C#. Al valor por
defecto el comportamiento no cambia, así que la firma anterior sigue válida.

Se agregaron 9 pruebas que corren **fuera** de los valores por defecto. **Tres de ellas
fallan sobre el código sin arreglar** — o sea que son pruebas de verdad, no decoración.

Se barrieron las 21 perillas buscando el mismo patrón: **era la única**.

### Para retomarlos hay UNA condición

El programa guarda, en cada resultado parcial, **con qué versión del código se calculó**.
Si retomás desde otra versión, se niega a mezclarlos.

Los 57 se calcularon con **`7fbab53`**. Así que en la otra máquina:

```bash
git checkout 7fbab53
```

y después el mismo comando de abajo. Si estás en otra versión, los 57 se recalculan desde
cero — funciona igual, pero perdés ~13 horas.

### El comando

```bash
python tools/bt2_absorption_param_sweep.py run --stage all --resume \
  --max-hours 8 --contracts "GC 02-26" \
  --data-dir "<ruta a DataNT8>" \
  --output "<ruta a DataNT8>/sweep_7fbab53_GC02-26"
```

Y lo mismo cambiando `GC 02-26` por `GC 04-26`, `GC 06-26` y `GC 08-26`, **cada uno con su
propia carpeta de salida**.

### Cuánto tarda: mucho más de lo que parece

Las 57 configuraciones tardaron **13 horas**. Y **una sola** de ellas tardó **6,7 horas** —
las que aflojan los filtros generan tantas señales que el procesamiento explota.

Estimación para las 396 en total: **varios días**. Se puede cortar y retomar cuantas veces

## 7. Sobre los datos de crypto, si se retoma

Se investigó bastante y hay dos cosas que conviene no volver a descubrir:

**Binance dejó de publicar el mejor precio de compra/venta después del 2024-03-30.** Las
operaciones sí están al día. No hay archivo gratuito de libro de órdenes descargable en
bloque — se probaron cuatro fuentes y las cuatro fallaron al intentarlas.

**Eso resultó no importar.** Las operaciones de Binance ya traen **quién fue el agresor**
como dato del propio exchange, y el indicador sólo usaba el libro para adivinar eso mismo.
Se agregó soporte para usar el dato directo. La cobertura pasó de 320 días a **2.542**.

**El tamaño mínimo de precio cambia con el tiempo.** SOL pasó de `0.001` a `0.01` el
2024-10-14. Usar el valor actual sobre datos viejos daba un 85 % de precios «inválidos»
que no eran tales. Está resuelto en `specs/binance_tick_size_history.json`, con las fuentes
oficiales.

**Bitcoin en CME (MBT)** se midió: tiene **entre 34 y 245 veces menos operaciones por
sesión** que el oro. Mucho movimiento de órdenes, pocas operaciones. Para un indicador de
absorción podría ser interesante, pero con el tamaño de bloque actual una sesión da 22-162
bloques contra los 5.465 del oro.

## Nota para quien siga

Tres errores míos de hoy, por si ayudan a no repetirlos:

**Confié en el número más visible.** Conté doce perillas «decorativas» mirando cuántas
señales producían. Eran tres. Las otras nueve cambiaban cuánto **vivía** cada señal, que yo
no estaba mirando.

**Comparé cosas que no eran comparables.** Dos carpetas con distintos archivos de datos, y
concluí que había una regresión que no existía.

**Estimé tiempos sin medir.** Me equivoqué por factores de 3× y 5×, siempre extrapolando
desde el caso rápido. Los tiempos reales tienen una dispersión de 13× entre configuraciones.

El patrón común: **elegí lo fácil de mirar y lo traté como si fuera todo el asunto.**
